# log_triage

把几万行日志压成一页排查报告的小脚本。零依赖，只用 Python 标准库。

## 它解决什么问题

排日志的瓶颈从来不是「看不到报错」，而是**看不过来**：

- **噪音多**：info 级别日志占绝大多数，真正的报错夹在中间
- **重复多**：一次失败重试能把同一个异常刷几百遍，把唯一的真根因埋掉
- **定位靠猜**：报错只说「下单失败」，在哪个文件哪一行得再翻一遍堆栈

`log_triage.py` 做三件事：解析、聚合、定位，最后输出一份 Markdown 报告。

## 三步原理

1. **解析**：把纯文本切成结构化记录（时间、级别、来源、消息、堆栈）。关键是识别**堆栈续行**并挂到上一条记录上，包括顶格打印的 `java.lang.XxxException` 首行。
2. **聚合**：给每条记录算一个「签名」，把同类报错合并。签名的关键是**归一化**——抹掉内存地址、长数字、行号这些每次都变的部分。签名优先取堆栈里的异常行，因为它比消息体稳定。
3. **定位**：从堆栈里抽出第一个「文件:行号」，直接给出可疑代码位置。

## 用法

```bash
# 默认只看 ERROR 及以上
python log_triage.py app.log

# 放宽到 WARN
python log_triage.py app.log WARN

# 存成报告文件
python log_triage.py app.log ERROR > 排查报告.md
```

无需安装任何第三方库，Python 3.8+ 即可。

## 输出示例

```markdown
# 日志排查报告：1284 条告警，归并为 27 类

## 1. java.lang.NullPointerException: "order" is null

- 出现次数：612
- 时间范围：2026-10-14 09:31:02 ~ 2026-10-14 10:12:44
- 来源：com.demo.OrderService
- 可疑代码位置：`OrderService.java:187`
```

报告按出现次数从多到少排序，默认只展示前 10 类，其余只统计数量。

## 可调参数

| 位置 | 说明 |
|---|---|
| `HEAD` | 日志头部行格式。你的日志格式不同就改这个正则 |
| `CONT` | 堆栈续行判定规则 |
| `NOISE` | 归一化规则，决定哪些部分会被抹掉 |
| `LEVELS` | 级别优先级，默认只看 ERROR 及以上 |
| `report(groups, top=10)` | 报告展示前 N 类 |

## 已知边界

说清楚它**不**解决什么，比说它能做什么更重要：

- **不适合跨服务链路追踪**。那需要 `traceId` 在各环节贯通，是另一个工程问题。
- **不适合实时告警**。事后排查脚本不能替代监控系统，该上的告警还是要上。
- **效果上限取决于日志格式的规范程度**。格式五花八门时，`HEAD` 正则的命中率会明显下降；把日志格式统一了，收益比写脚本更大。
- 需要交互式浏览、SQL 查询日志时，用成熟工具更合适（见下）。

## 与其他工具的关系

这不是替代品，而是补位：

- [tstack/lnav](https://github.com/tstack/lnav)（BSD-2-Clause）——终端日志浏览器，功能完整，适合日常交互式排查
- [allinurl/goaccess](https://github.com/allinurl/goaccess)（MIT）——Web 访问日志的报表工具，场景不同

本脚本的定位是：把结论固化成一份能发给别人的报告，或者接进自己的流程（比如自动提缺陷单）。
